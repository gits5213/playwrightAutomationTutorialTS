# Lesson 48 — Professional `.gitignore`

## 1. What You Will Learn
- What `.gitignore` does
- Which Playwright and Node folders must stay off GitHub
- How to ignore `.env` while keeping `.env.example`

## 2. Why This Matters in Real Projects
`node_modules/` is huge and rebuildable. Reports contain machine-specific paths. `.env` can hold passwords. If those land on GitHub, you get noisy diffs, leaked secrets, and clones that fight your laptop. Ignore rules are a safety net.

## 3. Concept in Plain English
Git tracks files unless you list a pattern in `.gitignore`. Ignored files still exist on disk. `npm install` and `npx playwright test` still create them. Git simply will not stage them.

## 4. Real-Life Analogy
A suitcase packing list says “do not pack the kitchen sink.” `.gitignore` is that list. The sink still belongs in the kitchen (`node_modules/` still belongs on your machine).

## 5. Prerequisites
- [Lesson 46](46-git-fundamentals.md)

## 6. Files We Will Create or Modify
- `.gitignore` (this repo already has one)
- `.env.example` (tracked); `.env` (ignored)

## 7. Step-by-Step Instructions
1. Open `.gitignore` at the repo root.
2. Confirm secrets, dependencies, Playwright output, auth, and OS junk are listed.
3. Confirm `!.env.example` **un-ignores** the template.
4. Run `git status`. Those folders should not appear as untracked after a test run.

## 8. Complete Code Example

```gitignore
.env
.env.*
!.env.example

node_modules/

test-results/
playwright-report/
blob-report/
playwright/.cache/
playwright/.auth/

.DS_Store
.idea/
*.log
```

## 9. Line-by-Line Explanation
- `.env` / `.env.*` — local secrets and overrides.
- `!.env.example` — exception so teammates see required variable **names**.
- `node_modules/` — reinstall with `npm install` / `npm ci`.
- `test-results/`, `playwright-report/`, `blob-report/` — generated by runs.
- `playwright/.auth/` — cookies and storage state. Never upload sessions.
- `*.log`, `.DS_Store` — machine noise.

## 10. How to Run It

```bash
npx playwright test tests/basic/registration-heading.spec.ts --project=chromium
git status
```

## 11. Expected Result
The report folder exists on disk. `git status` does **not** list `playwright-report/` or `test-results/` as new files.

## 12. Common Beginner Mistakes
- Ignoring `src/` or `tests/` (those **belong** in Git)
- Ignoring `package-lock.json` (CI needs it for `npm ci`)
- Committing `.env` before the ignore rule existed (must rotate secrets)

## 13. How to Debug It
If a file still shows up, it may already be **tracked**. `.gitignore` does not untrack. `git rm --cached path` removes it from Git but keeps the disk copy. Ask a mentor before running that on shared files.

## 14. Best Practices
- Ignore outputs, not sources
- Keep `.env.example` with `BASE_URL` and `REGISTRATION_FORM_URL` examples
- Review `.gitignore` in the same PR as new tools (Allure, coverage)

## 15. What NOT to Do
- Do not ignore `playwright.config.ts`, `.github/workflows/`, or lesson docs
- Do not put secrets in `.env.example`

## 16. Hands-On Exercise

## 17. Challenge Exercise

## 18. Knowledge Check / Quiz
1. Why ignore `node_modules/`?
2. Why keep `.env.example`?
3. Why ignore `playwright/.auth/`?

**Answers:** 1) Rebuildable and huge 2) Documents variable names without secrets 3) Sessions are credentials.

## 20. Architect's Notes
Ignore files are security and hygiene. They are not a substitute for CODEOWNERS or protected `main`. If a report must be shared, upload it as a CI **artifact** (Lesson 53), not as a commit.
